# HAXcms MCP: Implementation Plan

Version 1.0 (2026-09-30). Target: `@haxtheweb/haxcms-nodejs` 26.8.1. Stack: Python 3.12+, FastMCP 4.x.

This plan is written for a coding agent that will build the whole project with minimal human
intervention, one Phase at a time, in one repository and one working tree. Read Section 0 before
doing anything.

Vocabulary: every capitalised term (Site, Item, Page Break, Anchor, Outbound Budget, Phase, Session,
Handoff...) is defined in [`CONTEXT.md`](./CONTEXT.md). The HTTP contract is in
[`docs/haxcms-api-reference.md`](./docs/haxcms-api-reference.md) (referred to below as **API-REF**
with section numbers). Architecture decisions that were deliberately made are in `docs/adr/`.

---

## 0. Read this first: how to execute this plan

### 0.1 Documents and read order at the start of every Session

1. `PLAN.md` Section 0, then the section for the Phase you are about to do (only that Phase).
2. `CONTEXT.md` in full (it is short).
3. `PROGRESS.md` in full: what earlier Phases built, verified facts, and deviations.
4. `docs/haxcms-api-reference.md` sections named in the Phase's "Read first" list.
5. `docs/fastmcp-notes.md` (written in Phase 0) for the exact FastMCP APIs in use.

### 0.2 Non-negotiable rules

- **One agent, one working tree, sequential Phases.** Do not create git worktrees or parallel
  branches. All code lives in this repository (`haxcms-mcp/`). Never write into `../haxcms-nodejs`.
- **`PLAN.md` is read-only for the implementing agent.** If reality contradicts the plan, follow
  reality, and record the deviation in `PROGRESS.md` under the Phase. Do not edit this file.
- **`PROGRESS.md` is the Handoff.** Update it at the end of every Phase (template in
  `PROGRESS.md`). It is the only memory that survives a Session change.
- **Commit per completed task**, on `main`, Conventional Commits (Section 0.6). Tag `phase-NN` at
  the end of each Phase after all its suites pass.
- **Every Phase ends with four suites** (unit, integration, regression, functional where the Phase
  has user-facing features) and all previous Phases' suites still green (Section 6).
- **Verify before relying.** API-REF marks facts to "verify". Verify against the running test
  instance in the Phase that first uses the fact, and write the result into `PROGRESS.md` under
  "Verified facts". Later Phases read it from there.
- **No scope creep.** Out of scope (do not build, even if easy): HAXcms admin/system configuration
  writes (`configuration/*`, `PATCH themes|blocks|skeletons`), HAXiam user access, media provider
  search, anything under `haxiam-managed` deployment profile, spawning HAXcms from the MCP server
  in production, prompts beyond the four listed, a web UI.

### 0.3 Session protocol (Claude Code)

The build alternates between independent Phases and one pair of overlapping Phases.

| Phases | Relationship | Session rule |
|---|---|---|
| 0 | independent | fresh Session |
| 1 | independent (all later Phases depend on its code, but not on its context) | fresh Session |
| 2 | independent | fresh Session |
| 3 and 4 | **overlapping**: Page Details are saved through the same content endpoint that Phase 4 wraps, and Phase 4's Page Break builder needs Phase 3's Item model in working memory | **one Session for both**: finish Phase 3 (all suites, tag, `PROGRESS.md`), run `/compact`, then start Phase 4 in the same Session |
| 5 | independent (calls Phase 4 service functions by import only) | fresh Session |
| 6 | independent | fresh Session |
| 7 | independent (calls Phase 3 bulk-create by import only) | fresh Session |
| 8 | independent | fresh Session |
| 9 | independent | fresh Session |

Procedure between independent Phases: finish the Phase exit checklist (Section 0.5), write the
`PROGRESS.md` entry, commit, tag, then run `/clear`. In the new Session, start with Section 0.1.

Fallback when `/clear` is unavailable: the orchestrating agent spawns **one** subagent per Phase
(never two at once), gives it this Section 0 plus its Phase section, waits for it to finish and
report, then spawns the next. For Phases 3 and 4 the same subagent handles both and is told to
compact between them.

### 0.5 Definition of done for a Phase

1. Every task in the Phase has a commit.
2. `uv run ruff check . && uv run ruff format --check . && uv run mypy src` pass.
3. `uv run pytest -m "unit"` passes; `uv run pytest -m "integration or functional or regression"`
   passes against a spawned HAXcms; all earlier Phases' tests still pass (this is the regression
   rerun).
4. New tools appear in the tool-schema snapshot (`tests/regression/snapshots/tool_schemas.json`),
   and the snapshot diff was reviewed and committed deliberately.
5. `PROGRESS.md` has the Phase entry (built, verified facts, deviations, known gaps).
6. Tag `phase-NN` created on the final commit.

### 0.6 Commit conventions

Conventional Commits (https://www.conventionalcommits.org). Types used: `feat`, `fix`, `test`,
`docs`, `chore`, `refactor`, `build`, `ci`. Scope is the module or Phase area: `core`, `auth`,
`ratelimit`, `sites`, `pages`, `outline`, `content`, `blocks`, `catalog`, `files`, `settings`,
`imports`, `converters`, `exports`, `resources`, `prompts`, `harness`, `tests`, `docs`, `ci`.

Examples:

```
feat(auth): login, refresh, and site-token acquisition for HaxcmsClient
test(pages): functional suite for create/rename/delete page journey
docs(progress): phase 3 handoff
chore(release): tag phase-03
```

Every commit message body ends with the attribution line required by the environment (see the
system reminder in the Session; if none is present, omit it).

## 1. Goals, scope, and non-goals

**Goal.** An Agent connected to this MCP server can do everything the written "New User Script"
tutorial does, and everything else a human can do in the HAX dashboard and editor on a self-hosted
HAXcms NodeJS instance: create and manage Sites, build and reorder Outlines, author Page Content
with the full Block Catalog, upload and use Files, change Themes and settings, import documents and
other platforms' sites, export and configure publishing. The Agent does this through Tools with
precise parameters, discovers what is legal through Resources, and can be guided by Prompts.

**In scope** (decided with the product owner, see ADR-0001):

- HTTP client of a running HAXcms NodeJS instance; JWT login with username and password.
- Hand-designed Tools for Sites, Outline, Pages, Content, Blocks, Files, Settings, Exports, git
  publishing settings.
- Typed Block Tools for the Core Blocks (Appendix B) plus a validated generic `add_block`.
- Text-anchor addressing inside Page Content.
- Composite-only Document Import and Platform Import Tools.
- Generated Tools for the twelve stateless Converters, produced at build time from the vendored
  OpenAPI spec (ADR-0002).
- Resources for catalog, sites, outlines, content. Four Prompts.
- stdio and streamable HTTP transports.
- Outbound Budget (global token bucket, 4 requests per second, burst 8, env-overridable) with
  Back-off on 429.
- Read-Only Mode (off by default) and destructive hints.
- Test harness that installs and spawns a real HAXcms NodeJS for integration, functional,
  regression, and end-to-end tests.

**Non-goals.** See Section 0.2. Also: no local reimplementation of sanitisation, rendering, or
git; no multi-user support (HAXcms NodeJS has one Login User); no persistence in the MCP server
beyond in-memory token caches.

## 2. Architecture

### 2.1 Layers

```
 Agent (Claude, etc.)
   │  MCP (stdio | streamable HTTP)
   ▼
┌──────────────────────────────────────────────────────────────────────────┐
│ haxcms_mcp.server            FastMCP app: registers tools/resources/prompts│
│   middleware/                 read-only gate, error translation, logging   │
│   tools/                      thin @tool functions: validate args → service│
│   resources/  prompts/                                                     │
├──────────────────────────────────────────────────────────────────────────┤
│ haxcms_mcp.services          domain operations, no MCP types               │
│   sites, outline, pages, content, blocks, files, settings, imports, exports│
│   content/  parser, anchors, page_break, serializer, media_schema          │
│   catalog/  bundled block catalog + live merge                             │
├──────────────────────────────────────────────────────────────────────────┤
│ haxcms_mcp.client            HaxcmsClient (httpx.AsyncClient)              │
│   auth (login/refresh/tokens) · budget (token bucket) · retry · envelope   │
│   endpoints: system_*, site_* typed request/response helpers               │
├──────────────────────────────────────────────────────────────────────────┤
│ haxcms_mcp.models            pydantic v2 models for Items, Sites, Files... │
│ haxcms_mcp.config            Settings (pydantic-settings, HAXCMS_MCP_*)    │
│ haxcms_mcp.generated         converters.py emitted by scripts/gen_tools.py │
└──────────────────────────────────────────────────────────────────────────┘
   │  HTTPS/HTTP
   ▼
 HAXcms NodeJS 26.8.1  (system API /system/api/v1, site API /_sites/{site}/x/api/v1)
```

Rules: tools never call httpx; services never import FastMCP; the client never knows about Blocks.
Each layer is unit-testable alone.

### 2.2 Request lifecycle of a write Tool

1. FastMCP parses arguments against the Tool's pydantic signature.
2. Middleware: if Read-Only Mode and the Tool is not annotated `readOnlyHint=True`, raise
   `READ_ONLY`.
3. Tool resolves `site` (explicit argument or Default Site) and calls one service function.
4. Service acquires the per-Site `asyncio.Lock` (writes only), reads what it needs, computes the
   new state (e.g. new Page Content with a Page Break), and calls client endpoint helpers.
5. Client: ensure a valid Access Token (login or refresh), ensure the Site Token for that Site,
   `await budget.acquire()`, send, handle 429 with Back-off, unwrap the envelope, map errors to
   `HaxcmsMcpError`.
6. Service returns a pydantic model; tool returns `model.model_dump()`; middleware translates
   `HaxcmsMcpError` into a `ToolError` whose message is `[CODE] message. hint`.

### 2.3 Key mechanisms (specified once, used everywhere)

**AuthManager** (`client/auth.py`). State: `access_token`, `access_issued_at`, cookie jar (holds
`haxcms_refresh_token`), `user_token`, `site_tokens: dict[str, str]`. Methods:
`ensure_access()` (login if none; refresh if older than 12 min; on refresh failure, login again if
credentials exist, else raise `AUTH_REQUIRED`), `login(username, password)`, `logout()`,
`site_token(site)` and `user_token()` (both from connection-settings, API-REF §2.5, cached),
`invalidate()` on 403 "Invalid bearer token". In `HAXCMS_MCP_NO_AUTH` mode all of this is skipped
and no auth headers are sent.

**OutboundBudget** (`client/budget.py`). Token bucket: `rate` tokens per second, `capacity` burst,
`max_wait` seconds. `acquire()` waits until a token is available or raises `RATE_LIMITED` with the
projected wait. Single instance per process, shared by every request. Exposed metrics
(`tokens`, `waits`, `denials`) for tests.

**Retry policy** (`client/retry.py`). On 429: sleep `Retry-After` (cap 60 s, default 2 s) and retry
up to `HAXCMS_MCP_RETRY_MAX` times, counting against the budget. On connection errors and 502/503/504:
retry idempotent methods (GET, HEAD) only, exponential back-off 0.5 s, 1 s, 2 s. Never retry a
POST/PATCH/DELETE automatically.

**Envelope handling** (`client/envelope.py`). `unwrap(response) -> Any` returns `data`; maps 401 to
`AUTH_REQUIRED`/`AUTH_FAILED`, 403 with token message to `AUTH_FAILED` (after one refresh attempt),
403 with "disabled for this site" to `FEATURE_DISABLED`, 404 to `NOT_FOUND`, 400 to
`INVALID_ARGUMENT` (message included), 429 to `RATE_LIMITED`, 5xx to `UPSTREAM_ERROR`. Top-level
extra keys (`jwt`, `link`, `id`, `slug`) are preserved via `unwrap_full()`.

**Per-Site write lock** (`services/locks.py`). `async with site_lock(site):` around every service
write. Prevents two concurrent Tool calls from doing read-modify-write on the same Page in one
process.

**Page Break envelope** (`services/content/page_break.py`). `build_page_break(item: Item) -> str`
implements API-REF §5.2 exactly: every present detail emitted as `name="value"`, flags emitted as
`published="published"`, `locked="locked"`, `hide-in-menu="hide-in-menu"`,
`override-pathauto="true"`; absent details omitted. `save_content(site, item, body_html, schema)`
prepends the envelope and PATCHes. Golden tests pin the output.

**Block parser and Anchors** (`services/content/parser.py`, `anchors.py`). Parser: `lxml.html`
fragment parsing; top-level element children are Blocks; stray top-level text is wrapped in `<p>`.
`Block` = `{index, tag, attributes, text (normalised, whitespace-collapsed), html, preview (first
80 chars)}`. Anchor resolution: `resolve_anchor(blocks, anchor, occurrence, kind) -> Block`. Kind
`auto`: if the string matches `^[a-z][a-z0-9-]*(\[[^\]]+\])*$` it is a selector, else text. Text
match: case-insensitive substring on `text`, and also on `attributes` values for media blocks (so
"Songline_1" finds the image). Selector grammar: `tag`, `tag[attr]`, `tag[attr=value]`,
`tag[attr*=value]`, chained brackets. Zero matches → `ANCHOR_NOT_FOUND` with up to 10 block
previews; several matches without `occurrence` → `ANCHOR_AMBIGUOUS` listing each match's index and
preview; `occurrence` is `first`, `last`, or a 1-based integer.

**Serializer** (`services/content/serializer.py`). `serialize(blocks) -> str` joins block HTML with
newlines. Attribute quoting is double quotes; boolean attributes as `attr=""` are acceptable to
HAX (presence is truth) but the serializer emits the attribute name with the value given by the
tool (e.g. `card="card"` when the tool sets a flag) for readability.

**Media schema** (`services/content/media_schema.py`). Builds the `schema` array for content saves
from `media-image[source]`, `video-player[source]`, `img[src]`, `a11y-gif-player[src]`.

**Block Catalog** (`services/catalog/`). `bundled/*.json` one file per Core Block (Appendix B) with
`tag, title, description, attributes[{name, type, required, description, enum?}], slots[{name,
description}], example_html, agent_notes`. `CatalogService.get(tag)` merges live data from
`GET blocks/{tag}?include=haxProperties` and `GET schemas?filter.kind=haxProperties&...` when the
server has it (cache 10 minutes). `CatalogService.validate(tag, attributes)` checks tag is known
(bundled, live, or in `custom-elements`), attribute names are known or `data-*`/`slot`/`class`/`id`,
and enum values are legal; unknown tags raise `INVALID_ARGUMENT` listing the closest matches.

**File Sources** (`services/files/sources.py`). `resolve_source(source: str) -> (bytes, filename,
mimetype)`. `http(s)://` is fetched with httpx (size cap = HAXcms upload limit); `data:` URLs and a
`base64:<name>:<payload>` form are decoded (cap `HAXCMS_MCP_MAX_INLINE_BASE64_MB`); anything else is
a local path that must resolve inside one of `HAXCMS_MCP_INPUT_ROOTS` (default: current working
directory) or raise `FILE_SOURCE_ERROR`.

**Output directory** (`services/exports/output.py`). Export Tools write into
`HAXCMS_MCP_OUTPUT_DIR/<site>/<timestamp>-<name>.<ext>` and return `{path, bytes, mimetype}`; never
the bytes and never a URL.

### 2.4 Site addressing

Every Site-scoped Tool has `site: str | None = None`. Resolution: argument, else Default Site, else
`INVALID_ARGUMENT` "site is required; set HAXCMS_MCP_DEFAULT_SITE or pass site". Site Names are
normalised to lowercase and validated against `^[a-z0-9][a-z0-9-_]*$`.

### 2.5 Transports

`haxcms-mcp` CLI (`src/haxcms_mcp/__main__.py`): `haxcms-mcp` (stdio, default),
`haxcms-mcp --transport http --host 127.0.0.1 --port 8765 --path /mcp`. Logging goes to stderr only
(stdio safety). The Outbound Budget is process-wide regardless of transport.

## 5. Conventions

- **Tool names**: `verb_noun` snake_case, no prefix. Verbs: `list`, `get`, `create`, `update`,
  `set`, `add`, `replace`, `remove`, `move`, `delete`, `archive`, `clone`, `upload`, `import`,
  `export`, `search`, `login`, `logout`. Typed Block Tools are `add_<block>`.
- **Tool docstrings** are the Agent's manual: first line = what it does; then when to use it, the
  meaning of each parameter, what it returns, and the most common error. Mention related tools by
  name. Keep under 60 lines.
- **Annotations**: every Tool declares `readOnlyHint`, `destructiveHint`, `idempotentHint`,
  `openWorldHint=False`. Destructive Tools: `delete_page`, `delete_file`, `archive_site`,
  `remove_block`, `replace_block`, `set_page_content` (overwrites), `reorder_pages`,
  `restore_page_revision`.
- **Errors**: only `HaxcmsMcpError(code, message, hint=None, details=None)` escapes services.
  Codes: `AUTH_REQUIRED, AUTH_FAILED, READ_ONLY, RATE_LIMITED, NOT_FOUND, INVALID_ARGUMENT,
  ANCHOR_NOT_FOUND, ANCHOR_AMBIGUOUS, FEATURE_DISABLED, UPSTREAM_ERROR, UNSUPPORTED,
  FILE_SOURCE_ERROR, TIMEOUT`. The MCP message format is `[CODE] message. hint`.
- **Results**: pydantic models dumped with `mode="json"`, `exclude_none=True`. Writes return the
  resulting record. Block operations return `BlockOpResult{site, page_id, page_slug, operation,
  affected: [Block], block_count, saved: true}`.
- **Typing**: `mypy --strict` on `src/`; `from __future__ import annotations`; no `Any` in public
  signatures except where HAXcms returns free-form metadata (`dict[str, Any]`).
- **Style**: ruff default rule set plus `I` (isort), `UP`, `B`, `SIM`; line length 100.
- **Async**: everything async; services and client are `async def`; tests use `pytest-asyncio`
  in `auto` mode.
- **Logging**: `logging.getLogger("haxcms_mcp.<module>")`; never log tokens or passwords; log every
  outbound request at DEBUG as `METHOD path status ms`.
- **Docs in code**: each `services/*.py` module starts with a docstring naming the API-REF sections
  it implements.

## 6. Testing strategy

### 6.1 Tiers

| Tier | Marker | Needs HAXcms | What it proves | Where |
|---|---|---|---|---|
| Unit | `unit` | no | one module in isolation; HTTP mocked with `respx` | `tests/unit/test_pNN_*.py` |
| Integration | `integration` | yes | Tool → service → client → real HAXcms, via FastMCP in-memory client; assert on API responses **and** on disk state in the runtime dir (site.json, page HTML) | `tests/integration/test_pNN_*.py` |
| Functional | `functional` | yes | a user story from the tutorial or dashboard expressed only through Tool calls, asserting the outcome a human would see | `tests/functional/test_pNN_*.py` |
| Regression | `regression` | partly | (a) snapshot tests: tool schemas (names, params, annotations), Page Break output, serializer output, catalog contents; (b) the mandated rerun of all earlier Phases' suites | `tests/regression/` |
| End-to-end | `e2e` | yes | the whole tutorial journey through the real stdio transport as a subprocess | `tests/e2e/` |

Additional markers: `needs_chrome` (PDF exports), `slow`, `network` (fetches from the public
internet; skipped in CI unless `HAXCMS_MCP_TEST_NETWORK=1`).

### 6.2 Harness

`tests/harness/haxcms_runtime.py`:

### 6.3 Commands

```
uv run pytest -m unit                                  # fast, no Node
uv run pytest -m "integration or functional"           # spawns HAXcms once per session
uv run pytest -m regression                            # snapshots + reruns (see 6.4)
uv run pytest -m e2e                                   # full journey over stdio
uv run pytest                                          # everything
```

### 6.4 The regression suite, precisely

Each Phase N adds `tests/regression/test_pNN_snapshots.py` which pins: the JSON of every Tool's
schema and annotations registered so far (`snapshots/tool_schemas.json`, one file, updated
deliberately with `--snapshot-update`), and Phase-specific golden outputs (e.g. Page Break strings,
serialized pages, catalog JSON). The regression **run** for Phase N is `uv run pytest -m "not e2e"`
over the whole tree: it re-executes every earlier Phase's unit, integration, and functional tests.
A Phase is not done until that command is green.

Snapshot tooling: `syrupy` (pytest plugin). If unavailable, use plain JSON files compared with
`json.dumps(sort_keys=True, indent=2)`.

### 6.5 Coverage

`pytest-cov` on `src/haxcms_mcp`; report in CI; target 85% lines for `client/` and `services/`,
not enforced as a gate until Phase 9, where it becomes a CI gate at 80% overall.

## Appendix D: The tutorial journey as tool calls (source: "New User Script")

The end-to-end smoke test replays this list. Text in quotes is content from the script; media URLs
come from `tests/fixtures/`.

1. Login: `login` (or env credentials) → `whoami` shows the user.
2. Choose journey and name the course: `create_site("First")` fails with the spaces hint;
   `create_site("first-underscore-course", theme="clean-one")` succeeds; `get_outline` shows one
   page (Welcome/Home).
3. Add a new page: `create_page(title="page")` → appears below Welcome.
4. Rename: `update_page_details(title="A Designerly Engagement with the World")`.
5. Paste seven paragraphs: `add_paragraph` ×7 (or `set_page_content` with seven `<p>`), each call
   saves; `get_page_blocks` shows seven `p`.
6. Save and view: `get_page_content` via the public `GET items/{id}?include=content` path returns
   the paragraphs.
7. Heading above the last paragraph: `add_heading("Designing in the Prairie Spirit", level=2,
   anchor=<text of paragraph 6>, placement="after")`.
8. Faster heading: `add_paragraph("The First Secret is Noticing", anchor=<text of paragraph 3>,
   placement="after")` then `replace_block(anchor="The First Secret is Noticing",
   html="<h2>The First Secret is Noticing</h2>")`.
9. First image at top: `add_placeholder(kind="image", placement="prepend")`, then
   `upload_file(source=fixtures/Songline_1.png)`, then `replace_block(anchor="place-holder",
   html=<media-image ...>)` or directly `add_image_from_file(..., placement="prepend")`; set
   `alt`, `caption`, `citation` via `update_block`.
10. Second image after a paragraph: `add_image_from_file(source=fixtures/Songline_2.png, alt=...,
    caption=..., citation=..., anchor=<paragraph text>, placement="after")`.
11. Lecture video: `add_video(source=<url>, title=<title>, anchor=<last paragraph before first
    heading>, placement="after")`.
12. Two external links: `add_link(anchor=<paragraph text>, text="Watch it here.", url=<url>)` twice.
13. Verify: `get_page_blocks` sequence; `haxcms://sites/{site}/pages/{slug}` resource; on disk
    `pages/<id>/index.html`.
14. Share: `export_site(format="zip")` → file in Output Directory.
